# 기획 질문 은행

direct 의 1단계(맥락 수집)와 2단계(멈춤 ①)에서 읽는다. 순서는 늘 같다. 먼저 코드와 문서에서 추론하고, 추론이 약한 것만
묻는다. 질문은 AskUserQuestion 한 번에 4개 이하(목표 / 주 사용자 / 방향 / 구조)로 묶는다.

## 목차
1. 페이지 유형 감지
2. 추론 출처와 신뢰도
3. 질문 은행
4. 멈춤 ① 을 건너뛰는 경우
5. 콘텐츠 인벤토리
6. 답이 브리프로 가는 길

## 1. 페이지 유형 감지

신호가 둘 이상 겹치면 그 유형으로 정한다. 정해지면 `references/page-patterns/<유형>.md` 하나만 읽는다. 한 페이지가 두 유형을
섞을 때(강의를 파는 크리에이터 랜딩 = landing + content-portfolio, 리뷰 게시판이 붙은 PDP = commerce + community)만 두 파일을
읽고, 주 유형의 순서를 뼈대로 쓴다.

| 신호 (라우트 · 파일·컴포넌트 · 의존성 · 사용자 말) | 유형 | 하위 유형 |
|---|---|---|
| `/pricing` `/features` `app/(marketing)/`, `Hero` `Pricing` `Testimonials` 컴포넌트, "랜딩" "소개 페이지" | landing | saas-product |
| 스토어 링크(`apps.apple.com`, `play.google.com`), 딥링크 설정, "앱 다운로드" | landing | app-download |
| `/waitlist`, 이메일·휴대폰 한 칸 폼만 있고 제품 라우트가 없음, "사전 등록" "출시 알림" | landing | waitlist |
| `/contact` + 서비스 목록 + 사례, "견적" "상담 신청" "외주" | landing | service-agency |
| 날짜·장소·시간표 데이터, `/tickets` `/register`, "행사" "밋업" "웨비나" | landing | event |
| 개인 이름이 곧 브랜드(로고 대신 이름), `/about` `/newsletter` `/courses`, 뉴스레터·강의 결제 연동(Stibee·Substack·ConvertKit·클래스 판매 링크 등), "개인 브랜드" "뉴스레터" "강의 판매" | landing | creator |
| `/dashboard` `/app/*` `(app)/` 라우트 그룹, 인증 가드, `Sidebar`, 표·차트 의존성(`@tanstack/react-table`, `recharts` 등), "관리자" "어드민" | saas-app | dashboard · list · detail |
| `/settings` `/billing` `/onboarding` `/login` `/signup` | saas-app | settings · billing · onboarding · auth |
| `/products/[id]` `/category/*` `/cart` `/checkout`, 커머스·결제 SDK(Shopify·Medusa·PortOne·토스페이먼츠 등), `price` `discountRate` `stock` 필드, "상세페이지" "쇼핑몰" | commerce | PLP · PDP · cart · checkout |
| `/board` `/boards/[id]` `/community` `/write`, `Post` `Comment` `Board` 모델에 `views` `likes` `category` 필드, "게시판" "커뮤니티" | community | 게시판형 · 피드형 |
| `/posts/[slug]` `/blog`, MDX·contentlayer, RSS, "블로그" | content-portfolio | blog-index · article |
| `/work` `/projects/[slug]`, 이력서 PDF, "포트폴리오" | content-portfolio | portfolio-home · case-study |
| `/docs`, 문서 프레임워크(Nextra·Docusaurus·VitePress·Starlight·Fumadocs 등), "문서" "가이드" | content-portfolio | docs |

"상세페이지"는 국내에서 대개 커머스 상품 상세(PDP)를 뜻한다. 맥락이 SaaS 면 항목 상세(detail)로 읽는다.

## 2. 추론 출처와 신뢰도

| 출처 | 읽는 법 | 알 수 있는 것 |
|---|---|---|
| `package.json` `description`·`name`·의존성 | 한 줄 설명, 프레임워크와 도메인 SDK | 유형, 스택 |
| README 첫 문단 | "무엇을 누구를 위해" 문장을 찾는다. 설치법 부분은 건너뛴다 | 제품, 사용자, 목표 |
| 메타데이터(`<title>`, `metadata`, `og:*`) | 사람이 고른 한 줄 요약 | 약속(히어로 문장 후보) |
| 현재 히어로 카피·H1 | 이미 쓰고 있는 약속. 고칠 대상인지 유지할 대상인지 묻는다 | 목표, 톤 |
| CTA 라벨·`href` | "무료로 시작" → 가입, "문의하기" → 상담, "구매하기" → 결제 | 주 행동 |
| 가격 데이터(`plans` 배열, `pricing` 상수) | 플랜 수, 무료 여부, 통화 | `pricing` 섹션 가능 여부 |
| 내비 항목 | 사이트의 큰 영역과 우선순위 | 하위 페이지, 정보 구조 |
| 분석 이벤트(`track('signup_click')` 등) | 운영자가 실제로 세는 행동 | 주 행동, 성공 기준 |
| 데이터 모델·API 타입 | 필드 이름과 개수 | 표 열, 카드 내용, 콘텐츠 유무 |
| `public/` 에셋 | 스크린샷·로고·사진이 실제로 있는지 | 콘텐츠 인벤토리 |

| 신뢰도 | 기준 | 처리 |
|---|---|---|
| 높음 | 사용자가 직접 말했다, 또는 출처 둘 이상이 일치한다(README + CTA 라벨) | 묻지 않는다. 브리프 §1 표의 근거 열에 "가정(출처)"으로 적는다 |
| 중간 | 출처 하나뿐이다(README 한 줄만) | 묻되 추론한 선택지를 맨 앞에 "(추론)"을 붙여 둔다 |
| 낮음 | 의존성·파일 이름으로 짐작했다 | 열린 선택지로 묻는다 |

## 3. 질문 은행

모든 질문은 AskUserQuestion 형식(질문 · 짧은 header · 선택지 2–4개, 각 선택지는 라벨 + 설명)으로 낸다. "기타" 입력은 도구가
자동으로 붙인다. 추론한 선택지는 맨 앞에 두고 라벨 끝에 "(추론)"을 붙이며, 설명 첫머리에 근거를 쓴다(예: "README 추론:
'팀 일정 공유 도구'"). 질문 바로 위 채팅에는 추론 결과를 3–4줄로 먼저 보여준다.

### 3.1 목표 — header `목표`

질문: "이 페이지에서 방문자가 해야 할 한 가지 행동은 무엇인가요?"

| 유형 | 선택지 (라벨 — 설명) |
|---|---|
| landing | 가입·체험 시작 — 히어로·중간·끝 CTA 가 가입으로 / 상담·문의 — 끝에 `form` / 앱 설치 — 스토어 버튼·QR / 사전 등록 — 히어로 안 인라인 폼 |
| saas-app | 빨리 찾고 처리 — 목록·표 중심 / 현황 파악 — 대시보드 / 첫 가치 도달 — 온보딩·빈 상태 / 설정 완료 — 설정·폼 |
| commerce | 상품 발견·비교 — PLP / 구매 확신 — PDP / 결제 완료 — 장바구니·주문서 / 브랜드 경험 — 큐레이션 기획전 |
| community | 읽을 글 찾기 — 목록 밀도 / 글쓰기 참여 — 글쓰기 진입점 / 댓글·반응 — 상세 화면 / 지난 정보 검색 — 검색 |
| content-portfolio | 끝까지 읽기 — 본문 / 구독 — 뉴스레터 / 연락·채용 — 작업물 + 연락 / 답 찾기 — 문서 검색 |

추론 기본값: CTA 라벨과 분석 이벤트. 둘이 같은 행동을 가리키면 묻지 않는다.

### 3.2 주 사용자 — header `사용자`

질문: "주로 누가, 어떤 상황에서 이 화면을 보나요?"

선택지는 추론한 후보 2–3개로 만든다. 라벨은 사람(누구), 설명은 상황(기기 · 빈도 · 익숙함)이다. 상황이 구조를 바꾸기 때문이다.

| 유형 | 선택지 예 |
|---|---|
| landing | 처음 듣는 사람 — 모바일, 공유 링크로 유입, 10초 안에 판단 / 비교 중인 실무자 — 데스크톱, 가격·연동 확인 / 기존 고객 — 새 기능 확인 |
| saas-app | 매일 쓰는 운영자 — 데스크톱, 하루 수십 번 / 가끔 보는 관리자 — 주 1회 현황 확인 / 현장 사용자 — 모바일, 짧게 |
| commerce | 목적 구매자 — 검색으로 들어와 비교 / 둘러보는 사람 — 모바일, 취향 탐색 / 재구매 고객 — 빠른 결제 |
| community | 눈팅 위주 다수 — 모바일, 훑기 / 활발한 작성자 — 글·댓글 자주 / 검색 유입 — 특정 글 하나 |
| content-portfolio | 검색 유입 독자 — 글 하나 / 채용 담당자 — 1–2분 훑기 / 문서 사용자 — 특정 답 |

추론 기본값: README 의 "누구를 위한" 문장, 서비스 성격(B2B 면 데스크톱 실무자, 소비자 앱이면 모바일).

### 3.3 방향 — header `방향`

direct 가 채운다. 이 파일은 형식만 정한다. 선택지 2–3개, 서로 축이 2개 이상 달라야 하고 안전안 하나와 과감안 하나를 포함한다.
라벨은 「이름」, 설명은 스타일 + 레퍼런스 + 바뀌는 것 한 줄. 사용자가 레퍼런스(URL·브랜드·이미지)를 이미 줬으면 이 질문은 뺀다.

### 3.4 구조 — header `구조`

유형별 질문 하나. 선택지와 그 영향은 각 패턴 파일 6장에 있다.

| 유형 | 질문 | 선택지 | 추론 기본값 |
|---|---|---|---|
| landing | 보여줄 실제 제품 화면(스크린샷·영상)이 있나요? | 여러 장 / 한두 장 / 아직 없음 | `public/` 의 스크린샷·스토어 에셋 수 |
| saas-app | 여유형(comfortable)과 밀집형(compact) 중 어느 쪽인가요? | 여유형 / 밀집형 / 혼합(토글) | 열 6개 이상 표가 많으면 밀집형 |
| commerce | 큐레이션형(에디토리얼)인가요, 카탈로그형(밀도)인가요? | 큐레이션형 / 카탈로그형 / 혼합 | 상품 수와 필터 속성 수 |
| community | 목록형(클리앙·더쿠·디시 같은 게시판)인가요, 피드형(당근 동네생활·인스타 같은 카드 피드)인가요? | 목록형 / 피드형 / 혼합 | 글에 이미지 비중, `views`·`category` 필드 |
| content-portfolio | 글이 주인공인가요, 작업물이 주인공인가요? | 글 / 작업물 / 둘 다 | `/posts` 와 `/work` 라우트 |

## 4. 멈춤 ① 을 건너뛰는 경우

확실한 문항은 빼고 남은 것만 묻는다. 뺀 문항은 브리프 §1 표의 근거 열에 "가정(출처, 신뢰도)"으로 적는다. 사용자는
멈춤 ②(브리프 승인)에서 가정을 고칠 수 있다. 어떤 경우든 추론 결과 3–4줄은 채팅에 먼저 보여준다.

| 상황 | 처리 |
|---|---|
| 목표·사용자·구조가 모두 신뢰도 높음 | 방향 한 문항만 묻는다. 방향은 사용자 취향이라 코드로 추론하지 않는다 |
| 방향이 정해져 있다(레퍼런스 URL·이미지·브랜드·프로필·스타일을 줬다, 기존 브리프의 방향을 이어 간다) | 레퍼런스가 곧 방향이다. 방향 문항은 빼고 추론하지 못한 목표·사용자·구조 문항만 묻는다. 방향은 프로필에서 뽑은 요약 하나로 보여주고, 변주("더 과감하게"·"더 차분하게")는 사용자가 원할 때만 만든다. 남은 문항이 없으면 3단계로 |
| 사용자가 요청에 이미 적었다("게시판형으로 목록 화면 설계해줘, 레퍼런스는 클리앙") | 적힌 문항은 묻지 않는다 |
| "알아서 해", "질문 말고 바로" | 묻지 않는다. 방향은 추천안 하나를 이유와 함께 정하고 브리프에 적는다 |
| 퀵 모드(컴포넌트 하나) | 이 파일을 쓰지 않는다. 퀵 모드는 구조 설계를 하지 않는다 |

질문이 하나만 남아도 AskUserQuestion 을 쓴다. 채팅으로 물으면 답이 흩어진다.

## 5. 콘텐츠 인벤토리

질문하기 전에 만든다. 구조를 짤 때 섹션마다 이 표를 보고 넣을지 뺄지 정한다. 지어내지 않는다: 없는 콘텐츠는 섹션을 빼거나
`TODO(카피)`·`TODO(이미지)` 자리만 남긴다.

| 항목 | 상태 | 출처 | 처리 |
|---|---|---|---|
| 예: 제품 스크린샷 | 있음 | `public/screens/*.png` 3장 | `hero-split`, `feature-alternating` 에 사용 |
| 예: 고객사 로고 | 없음 | — | `logo-cloud` 생략 |
| 예: 고객 후기 | 필요 | 베타 사용자 인터뷰 예정(사용자 답) | `testimonials` 자리에 `TODO(카피)` 1개, 오픈 전 채움 |
| 예: 사업자 정보 | 필요 | 유료 결제 있음 | `footer` 에 `TODO(사업자 정보)` |

- **있음**: 코드·에셋·문서에서 확인했다. 그대로 쓴다.
- **필요**: 이 페이지에 있어야 하는데 아직 없다. 자리를 남기고 브리프 §1 '없는 콘텐츠와 처리' 행에 적어 사용자가 채우게 한다.
- **없음**: 없고, 이 구조에서는 빼도 된다. 섹션을 생략한다.

유형별로 먼저 확인할 항목: landing — 제품 화면·로고·후기·수치·가격·FAQ 답·OG 이미지·사업자 정보 / saas-app — 데이터 모델·
지표 정의·빈 상태 문구 / commerce — 상품 이미지 비율·리뷰·배송·교환 정책·상품 정보 고시 / community — 게시판 목록·말머리·레벨
규칙·운영 규칙 / content-portfolio — 글 데이터·커버 이미지·작업물 이미지·결과 수치.

## 6. 답이 브리프로 가는 길

| 브리프 | 채우는 곳 |
|---|---|
| §0 한 줄 방향 | 3.3 답 (고른 안의 이름과 한 줄 요약) |
| §1 페이지 기획 · 목표 | 3.1 답 (또는 추론 + 출처) |
| §1 · 사용자 | 3.2 답. 기기·빈도까지 적는다 |
| §1 · 주/보조 행동 | 3.1 답 + 현재 CTA 라벨. 주 행동 1개, 보조 행동 최대 2개 |
| §1 · 있는/없는 콘텐츠 | 5장 인벤토리 표 |
| §1 · 근거·가정 열 | 칸마다 출처: 사용자 답 / 추론(출처) / 가정(출처, 신뢰도) |
