# SaaS·앱 화면 패턴

로그인 뒤에 쓰는 화면(대시보드·목록·상세·설정·폼·온보딩·인증·결제)의 구조를 정할 때 읽는다. 섹션 이름은
`${CLAUDE_PLUGIN_ROOT}/references/sections.md` 의 id 만 쓴다. 앱 화면은 설득하는 문서가 아니라 반복해서 쓰는 도구다.
그래서 기준이 랜딩과 다르다. 첫인상보다 매일 쓰는 속도가, 화려함보다 빈·로딩·오류 상태를 빠짐없이 설계하는 일이 먼저다.

어울리는 스타일: 비전문 운영자가 매일 쓰는 백오피스·설정은 `admin-calm`, 국내 관례(검색 조건 박스·엑셀)의 관리자 화면은 `kr-admin-classic`, 숫자 위주 대시보드는 `data-dense`, 실시간 관제는 `admin-console` (`${CLAUDE_PLUGIN_ROOT}/references/styles/_index.md`).

## 1. 하위 유형 (Subtypes)

앱은 페이지 종류가 하위 유형이다. 브리프 한 장은 보통 이 중 하나(또는 앱 골격 + 하나)를 다룬다.
백틱으로 쓴 하위 페이지 이름은 분류명이고 섹션 id 가 아니다. 브리프 섹션 표에는 `sections.md` id 만 쓴다.
섹션 id 와 헷갈리지 않게 앱 골격 페이지는 `shell-layout`, 폼 페이지는 `form-page` 로 부른다(섹션 id 는 `app-shell`·`form-section`).

| 하위 페이지 | 목적 | 대표 예시 성격 | 기본 섹션 순서 요약 |
|---|---|---|---|
| `shell-layout` | 어디서든 이동·검색·계정 | 모든 화면을 감싸는 틀 | app-shell: sidebar-nav(또는 상단바) + 본문 |
| `dashboard` | "지금 괜찮은가, 뭘 해야 하나" | 관리자 홈, 분석 홈 | page-header → kpi-row → chart-panel → data-table(처리할 것) |
| `list` | 많은 항목을 찾고 고르고 처리 | 주문·회원·문서·이슈 목록 | page-header → filter-bar → data-table 또는 card-list → pagination |
| `detail` | 항목 하나를 깊게 보고 고친다 | 주문 상세, 고객 상세 | page-header → 요약 key-value → 탭 → 활동 기록 (전체 페이지·드로어·분할) |
| `settings` | 설정을 찾아 바꾼다 | 계정·워크스페이스·알림 설정 | 설정 하위 내비 → settings-group 반복 → 위험 구역 |
| `form-page` | 새 항목 만들기·편집 | 상품 등록, 프로젝트 생성 | page-header → form-section 반복 → 하단 액션 (길면 stepper) |
| `onboarding` | 첫 가치까지 데려간다 | 가입 직후 첫 화면 | stepper(2–4단계) → empty-state(첫 행동) → 체크리스트 |
| `auth` | 로그인·가입 | 로그인, 회원가입, 비밀번호 찾기 | 로고 → 제목 → 소셜 로그인 → 이메일 폼 → 보조 링크 |
| `billing` | 플랜·결제·영수증 | 구독 관리 | 현재 플랜 → 사용량 → 결제 수단 → 결제 내역 표 |

## 2. 섹션 순서와 이유

### 2.0 공통 규칙

**밀도(density)** — 6장의 구조 질문으로 정하고 화면 전체에 같은 값을 쓴다.

| 레버 | 여유형 (comfortable) | 밀집형 (compact) |
|---|---|---|
| 표 행 높이 | 40–48px | 32–36px |
| 본문·셀 글자 | 14–15px | 13–14px |
| 셀 좌우 패딩 | 16px | 8–12px |
| 카드·패널 안쪽 여백 | 20–24px | 12–16px |
| 섹션 사이 간격 | 24–32px | 16–20px |
| 사이드바 폭 | 240–260px | 220–232px |
| 한 화면에 보이는 표 행 (1440×900) | 12–15행 | 18–22행 |

**page-header** — 모든 하위 페이지의 첫 섹션이다. 왼쪽: 브레드크럼(2단계 이상일 때만) → 제목(20–24px) + 항목 수 →
설명 한 줄(선택). 오른쪽: 보조 행동(내보내기, 더보기 `...`) → 주 행동 버튼 1개. 높이 64–88px.
주 행동 버튼이 페이지마다 같은 자리(오른쪽 위)에 있어야 손이 기억한다.

**filter-bar** — 목록 바로 위. 왼쪽 검색(240–320px, 플레이스홀더에 검색 대상 명시) → 필터 드롭다운·칩 → 오른쪽
보기 전환·열 설정. 적용된 필터는 칩으로 보여주고 "모두 지우기"를 둔다. 필터·정렬·페이지는 URL 쿼리에 남겨
새로고침·공유·뒤로 가기에도 유지한다.

**상태 3종** — 목록·차트·패널마다 세 가지를 설계한다. 빠지면 실제 사용에서 가장 먼저 깨진다.

| 상태 | 설계 |
|---|---|
| 로딩 (loading) | 실제 행 높이와 같은 skeleton 행 5–8개. 스피너만 두면 화면이 출렁인다. 300ms 안에 끝나면 아무것도 띄우지 않는다 |
| 빈 상태 (empty) | 세 가지를 구분한다. 처음 써서 없음(무엇이 생기는지 + 주 행동 1개), 검색·필터 결과 없음(조건 보여주기 + "필터 지우기"), 권한 없음(누구에게 요청하는지) |
| 오류 (error) | 무엇이 안 됐는지 + "다시 시도". 필터·입력값은 지우지 않는다. 표 안에서 난 오류는 표 자리에서 보여주고 페이지 전체를 막지 않는다 |

**파괴적 행동(destructive action)** — 되돌릴 수 있으면 확인 모달 대신 바로 실행하고 "되돌리기" 토스트(5–8초)를 띄운다.
되돌릴 수 없으면 모달에 대상 이름, 결과("멤버 12명이 접근 권한을 잃어요"), 빨간 버튼을 둔다. 버튼 라벨은 "확인"이 아니라
동사("삭제")로 쓴다. 워크스페이스 삭제처럼 큰 일은 이름을 직접 입력하게 한다.

### 2.1 shell-layout (`app-shell` 섹션)

1. `sidebar-nav` — 위에서부터 워크스페이스 전환 → 검색(⌘K) → 주 영역 5–8개 → 구분선 → 설정·도움말 → 사용자 메뉴.
   폭 220–260px, 접으면 56–64px 아이콘 열. 주 영역이 8개를 넘으면 그룹 라벨로 묶는다.
2. 상단바(`nav` 변형, 상단 내비만 쓰는 경우) — 영역이 5개 이하이고 화면 폭을 표에 다 써야 할 때. 높이 56–64px.
3. 본문 — 최대 폭을 정한다. 표 화면은 꽉 채우고, 설정·폼은 640–800px 로 제한한다. 폼이 1440px 로 늘어나면 라벨과 입력이 멀어진다.
4. 모바일 — 주 영역 4–5개는 `bottom-tab-bar`(56px + safe-area), 나머지는 "더보기" 탭이나 드로어로.

### 2.2 dashboard

1. `page-header` — 제목, 기간 선택(오늘·7일·30일·직접), 내보내기.
2. `kpi-row` — 3–5개. 각 지표에 비교 기준(전 기간 대비 증감)과 정의(툴팁)를 단다. 숫자만 있으면 좋은지 나쁜지 모른다.
3. `chart-panel` (주) — 전체 폭. "이번 주 매출이 왜 줄었나"처럼 답할 질문 하나를 제목으로 쓴다.
4. `chart-panel` × 2 (보조) — 반반. 주 차트의 원인을 나눠 본다(채널별, 상품별).
5. `data-table` — "처리할 것"(미처리 주문, 실패한 결제). 대시보드의 끝은 행동으로 이어져야 한다.

왜 이 순서인가: 위에서 아래로 "괜찮은가 → 무엇이 변했나 → 왜 변했나 → 무엇을 하나"로 내려간다. 가입 직후처럼
데이터가 없으면 `kpi-row` 자리에 온보딩 체크리스트를 먼저 둔다(2.7).

### 2.3 list

1. `page-header` — 제목 + 총 개수 + 주 행동("새 주문").
2. 상태 탭(전체·진행 중·완료·보관) — 상태마다 할 일이 다른 목록(미처리 → 처리)이면 `filter-bar` 맨 앞에 세그먼트로 둔다.
3. `filter-bar`
4. `data-table` 또는 `card-list` — 아래 표로 고른다. 행을 선택하면 표 위(또는 하단 고정)에 일괄 작업 바가 나타난다.
5. `pagination` — 페이지 번호 + 페이지당 개수(20·50·100). 무한 스크롤은 위치·선택 상태를 잃어 업무용 목록에 맞지 않는다.

| 조건 | `data-table` | `card-list` |
|---|---|---|
| 항목끼리 값을 비교한다 (금액·날짜·상태) | ✓ | |
| 열이 4개 이상 | ✓ | |
| 정렬·일괄 선택이 필요하다 | ✓ | |
| 이미지가 식별의 핵심이다 (상품, 디자인 파일) | | ✓ |
| 항목 수가 적고(20개 이하) 각각이 큰 단위다 (프로젝트) | | ✓ |
| 모바일이 주 사용 환경이다 | | ✓ (표는 2줄 행으로 변환) |

표 세부: 숫자 열은 오른쪽 정렬 + `font-variant-numeric: tabular-nums`, 텍스트 열은 왼쪽 정렬, 헤더는 sticky,
첫 열(이름)은 가로 스크롤 시 고정. 상태는 색만으로 구분하지 않고 텍스트 배지를 쓴다.

### 2.4 detail

세 가지 배치 중 고른다.

| 배치 | 언제 | 수치 |
|---|---|---|
| 전체 페이지 | 탭이 3개 이상, 편집이 길다, URL 로 공유한다 | 본문 최대 1080–1200px |
| 드로어 (drawer) | 목록에서 훑어보며 하나씩 확인한다. 목록 맥락을 유지해야 한다 | 오른쪽 480–640px, 화면의 40% 이내 |
| 분할 (split) | 분류·처리(triage)를 연속으로 한다 (문의함, 이슈) | 목록 360–420px + 상세 나머지 |

순서: `page-header`(제목, 상태 배지, 주 행동, 이전·다음 항목 이동) → 요약 key-value(2–3열, 라벨 12–13px 회색 + 값 14–15px)
→ 탭(상세·활동·설정) → 활동 기록(누가 언제 무엇을, 최신이 위). 요약을 탭 위에 두는 이유는 탭을 넘겨도 "지금 무엇을 보고
있는지"가 남아야 해서다.

### 2.5 settings

1. 설정 하위 내비(`sidebar-nav` 변형) — 왼쪽 세로 목록(180–200px) 또는 상단 탭. 개인 설정과 워크스페이스 설정을 그룹으로 나눈다.
2. `settings-group` 반복 — 왼쪽 1/3 에 그룹 제목 + 설명, 오른쪽 2/3 에 컨트롤. 설명이 있어야 무엇이 바뀌는지 안다.
3. 저장 — 그룹마다 저장 버튼을 두거나, 토글처럼 즉시 반영되는 항목은 자동 저장 + 토스트. 한 화면에 두 방식을 섞으면
   어떤 게 저장됐는지 헷갈리므로 그룹 단위로 통일한다. 저장 안 한 변경이 있는데 떠나려 하면 경고한다.
4. 위험 구역(danger zone, `settings-group` 변형) — 맨 아래, 빨간 테두리 그룹. 워크스페이스 삭제·소유권 이전.

### 2.6 form-page

1. `page-header` — "새 상품 등록" + 취소.
2. `form-section` 반복 — 관련 필드 3–6개씩 묶고 섹션 제목을 단다. 라벨은 입력 위(왼쪽 라벨은 라벨 길이가 제각각인 한국어에서
   정렬이 무너진다). 기본 1열, 짧고 관련된 필드(시·구, 시작일·종료일)만 2열.
3. 하단 액션 — 주 버튼은 필드 왼쪽 선에 맞춘다. 폼이 한 화면을 넘으면 하단 고정 액션 바(64px).
4. 단계가 3개 이상이거나 앞 단계 답에 따라 다음 질문이 바뀌면 `stepper`.

검증은 입력을 마친 뒤(blur) 필드 아래에 문장으로 보여주고, 제출 실패 시 첫 오류 필드로 스크롤·포커스한다.
필수 표시는 필수가 대부분이면 "(선택)"을, 선택이 대부분이면 `*` 를 쓴다.

### 2.7 onboarding · 빈 상태

1. `stepper` — 가입 직후 2–4단계(역할, 팀 이름, 초대). 단계마다 "나중에 하기"를 둔다.
2. `empty-state` — 첫 화면의 빈 목록이 곧 온보딩이다. 무엇이 여기에 생기는지 한 줄 + 주 행동 버튼 1개 + 가져오기(CSV 등)나
   문서 링크 같은 보조 행동 1개. 일러스트는 선택이고 버튼이 핵심이다.
3. 체크리스트(`stepper` 변형) — 첫 가치까지 3–5항목, 진행률 표시, 다 하면 사라진다. 대시보드 `kpi-row` 자리를 잠시 빌린다.

전체 화면 투어 모달을 첫 화면에 띄우지 않는다. 읽지 않고 닫는다. 대신 빈 상태와 체크리스트가 같은 일을 한다.

### 2.8 auth

로그인: 로고 → 제목("로그인") → 소셜 로그인 버튼(국내는 카카오·네이버가 먼저 오는 경우가 많다) → 구분선 "또는" →
이메일·비밀번호 → 로그인 버튼 → 비밀번호 찾기 · 회원가입 링크. 폼 폭 360–400px, 입력 높이 44–48px.
회원가입: 소셜 가입 → 이메일 가입 폼 → `agree-all`(5장) → 가입 버튼. 본인인증이 필요한 서비스만 휴대폰 인증 단계를 넣는다.
비밀번호 규칙은 입력 전에 보여주고, 입력 중에 항목별로 충족 여부를 표시한다.

### 2.9 billing

1. 현재 플랜(`settings-group`) — 플랜 이름, 금액, 다음 결제일, 플랜 변경 버튼.
2. 사용량(`kpi-row` 변형) — 한도가 있는 항목만 진행 바(사용/한도, 80% 넘으면 경고색).
3. 결제 수단(`settings-group`) — 카드 끝 4자리, 만료일, 변경.
4. 결제 내역 `data-table` — 날짜 | 내용 | 금액 | 상태 | 영수증. B2B 면 세금계산서 발행 정보(사업자 정보·담당자 이메일)를 이 화면에서 관리한다.
5. 해지 — 맨 아래 텍스트 링크. 숨기지 않되 강조하지도 않는다. 해지 시점과 데이터 보존 기간을 확인 화면에 적는다.

## 3. 첫 화면 계약 (Above the fold)

### 데스크톱 1440×900

- `app-shell` 이 고정되어 있고 `page-header` 의 주 행동 버튼이 오른쪽 위에 보인다.
- 목록: `filter-bar` + 표 행이 여유형 12행, 밀집형 18행 이상 보인다. 표 헤더는 스크롤해도 남는다.
- 대시보드: `kpi-row` 전체와 주 `chart-panel` 의 제목·축이 보인다. "처리할 것" 표가 첫 화면 밖이면 `kpi-row` 옆에 건수 배지로라도 올린다.
- 상세: 제목·상태·주 행동·요약 key-value 가 스크롤 없이 보인다.

### 모바일 390×844

- 상단바 56px(뒤로·제목·검색·주 행동) + `bottom-tab-bar` 56px + safe-area. 남는 본문은 약 640px.
- 목록은 2줄 행(64–72px) 기준 7–9개가 보인다. 필터는 버튼 하나로 모아 `bottom-sheet` 로 연다.
- 주 생성 행동은 상단바 `+` 나 `fab`(56px, 탭 바 위 16px) 중 하나만 쓴다.
- 표의 열을 줄이지 말고 행을 카드형 2줄로 바꾼다. 1줄: 이름 + 핵심 값(오른쪽), 2줄: 상태 · 날짜.

## 5. 한국 관례

- **약관 동의**: `agree-all` — "전체 동의" 체크박스 아래에 개별 항목을 둔다. 항목마다 (필수)/(선택) 표기와 "보기"(펼침 또는
  시트). 전체 동의를 누르면 선택 항목까지 체크되고, 개별 항목을 하나라도 풀면 전체 동의도 풀린다. 선택 동의 없이도 가입이
  되어야 한다. 만 14세 이상 확인이 필요하면 별도 항목으로 둔다. 정확한 필수 항목은 서비스 성격과 법령 안내를 확인한다.
- **휴대폰 본인인증**: 실명·연령 확인이나 결제 등 실제로 필요한 서비스에서만 가입·결제 직전 단계로 넣는다. 필요 없는데
  넣으면 가입 이탈만 늘어난다. 인증 수단 선택 → 외부 인증 창 → 결과 반환 흐름이라 별도 `stepper` 단계로 그린다.
- **주소 입력**: [우편번호 찾기] 버튼 → 우편번호·기본 주소(읽기 전용, 검색 결과로 채움) → 상세 주소(직접 입력, 자동 포커스)
  세 줄 묶음. 주소 검색 서비스는 국내 우편번호 검색 API 를 쓰는 경우가 많다.
- **이름**: "이름" 한 칸. 성·이름을 나누지 않는다. 영문 이름이 필요한 경우(해외 결제·여권)만 따로 받는다.
- **날짜·시간**: `2026.10.14` 또는 `2026. 10. 14.` 형식, 시간은 `14:23`. 최근 항목은 "3분 전·어제"처럼 상대 시간,
  표에서는 절대 날짜로 통일해 정렬과 비교가 되게 한다.
- **금액**: `12,000원`. 표 안에서는 숫자만 오른쪽 정렬하고 단위 '원'은 헤더("금액(원)")로 올리면 숫자 열이 깔끔하다.
  큰 금액 KPI 는 "1.2억원"처럼 만·억 단위로 줄이되 툴팁에 전체 값을 둔다.
- **번호 형식**: 휴대폰 `010-0000-0000`, 사업자등록번호 `000-00-00000`(10자리) — 입력 중 하이픈 자동 삽입, 붙여넣기도 허용.
- **소셜 로그인 버튼**: 카카오·네이버·구글·애플 버튼은 각 플랫폼의 디자인 가이드(색·로고·문구)를 따른다. 임의로 색을 바꾸지 않는다.

## 6. 구조 질문 하나

> **여유형(comfortable)과 밀집형(compact) 중 어느 쪽인가요?**

| 선택지 | 바뀌는 것 |
|---|---|
| 여유형 — 가끔 쓰는 사람, 항목이 적다 | 행 40–48px, 14–15px, 카드형 패널 허용, 설명 텍스트 많이, 사이드바 240–260px |
| 밀집형 — 하루 종일 쓰는 운영자, 항목이 많다 | 행 32–36px, 13–14px, 표 중심, 열 설정·키보드 단축키, 패널 테두리 1px 로 구분(그림자 없음) |
| 혼합 — 사용자가 고른다 | 기본은 여유형, 목록 화면에 밀도 전환 토글. 두 값 세트를 토큰으로 만든다 |

코드에 표 컴포넌트와 열이 6개 이상인 화면이 많으면 밀집형을, 대부분 폼·카드면 여유형을 추론 기본값으로 둔다.

데이터·지표 정의가 없는 상태에서 그럴듯한 숫자와 차트를 그려 넣지 않는다.

| `kpi-row` | 지표 정의·실데이터 | 지표 이름만 확정하고 값 자리는 빈 상태("아직 데이터가 없어요"). 정의가 없으면 `TODO(지표 정의)` |
