# 랜딩 페이지 패턴

마케팅·랜딩 페이지의 섹션 구성을 정할 때 읽는다. 섹션 이름은 `${CLAUDE_PLUGIN_ROOT}/references/sections.md` 의 id 만 쓴다.
랜딩은 방문자 한 명을 한 가지 행동(가입·다운로드·신청·구매)으로 데려가는 문서다. 섹션 하나하나가 그 행동 앞의 망설임 하나를
없애는 역할을 맡아야 하고, 역할이 없는 섹션은 뺀다.

## 목차
1. 하위 유형 (Subtypes)
2. 섹션 순서와 이유
3. 첫 화면 계약 (Above the fold)
4. 와이어프레임
5. 한국 관례
6. 구조 질문 하나
7. 흔한 실수
8. 콘텐츠가 없을 때

## 1. 하위 유형 (Subtypes)

| 하위 유형 | 목적 | 대표 예시 성격 | 기본 섹션 순서 요약 |
|---|---|---|---|
| `saas-product` | 가입·체험 시작 | B2B·B2C 웹 서비스 소개 | nav → hero-split → logo-cloud → feature-alternating → cta-band → testimonials → pricing → faq → cta-band → footer |
| `app-download` | 스토어 설치 | 모바일 앱 출시·소개 | nav → hero-split(폰 화면) → proof-strip → feature-alternating → testimonials → faq → cta-band → footer |
| `waitlist` | 사전 등록·대기 명단 | 출시 전 제품, 크라우드펀딩 예고 | nav → hero-centered(폼 포함) → feature-grid → how-it-works → faq → cta-band → footer |
| `service-agency` | 상담·견적 문의 | 외주 개발, 디자인 스튜디오, 컨설팅 | nav → hero-type → logo-cloud → content-list(사례) → feature-grid → how-it-works → testimonials → form → footer |
| `event` | 참가 신청·티켓 구매 | 컨퍼런스, 밋업, 웨비나, 팝업 | announcement-bar → nav → hero-media → text-block → content-list(연사·일정) → pricing → faq → cta-band → footer |
| `creator` | 구독·문의·강의 판매 | 개인 브랜드, 뉴스레터, 1인 강의 | nav → hero-split → proof-strip → content-list → newsletter → testimonials → faq → footer |

판단이 애매하면 "방문자가 이 페이지에서 누르는 버튼이 무엇인가"로 정한다. 버튼이 "무료로 시작"이면 saas-product,
"앱 설치"면 app-download, "출시 알림 받기"면 waitlist, "상담 신청"이면 service-agency 다.
하위 유형 이름은 페이지 분류명이고 섹션 id 가 아니다. 브리프 섹션 표에는 `sections.md` id 만 쓴다.

## 2. 섹션 순서와 이유

### 2.0 공통 설득 순서

랜딩의 순서는 방문자 머릿속 질문의 순서를 따른다.

| 단계 | 방문자 질문 | 맡는 섹션 |
|---|---|---|
| 1 약속 (promise) | "이게 뭐고 나한테 뭐가 좋아?" | `hero-*` |
| 2 증거 (proof) | "진짜야? 누가 쓰는데?" | `logo-cloud`, `proof-strip`, `stats` |
| 3 작동 방식 (mechanism) | "어떻게 그게 되는데?" | `feature-alternating`, `bento-grid`, `feature-grid`, `how-it-works`, `demo`, `tabs-showcase` |
| 4 반론 처리 (objection) | "비싸지 않아? 내 경우에도 돼? 그만두기 쉬워?" | `testimonials`, `comparison`, `pricing`, `faq` |
| 5 행동 (action) | "그래서 지금 뭘 누르면 돼?" | `cta-band`, `form`, `newsletter` |

- 증거를 약속 바로 뒤에 둔다. 약속을 읽은 직후가 의심이 가장 큰 순간이라서다. 증거가 없으면 이 칸은 비우고 작동 방식으로 바로 간다.
- 작동 방식은 기능 목록이 아니라 "약속이 어떻게 지켜지는가"다. 약속과 관계없는 기능은 이 칸에서 뺀다.
- 가격은 반론 처리 칸에 둔다. 가치를 보기 전에 가격을 보면 비싸 보인다. 단, 가격 자체가 경쟁력(무료, 업계 절반)이면 히어로 보조 문장으로 끌어올린다.
- `faq` 는 마지막 CTA 바로 앞에 둔다. 행동 직전에 남은 망설임(환불, 해지, 데이터, 계약)을 없애는 자리다.

### 2.0.1 CTA 반복

- 주 CTA 는 세 번 나온다: 히어로, 작동 방식이 끝난 지점(중간 `cta-band`), 페이지 끝(`cta-band` 또는 `form`). 스크롤 어디서든 1.5화면 안에 CTA 가 하나 보이게 한다.
- 세 번 모두 같은 라벨·같은 목적지를 쓴다. 라벨이 바뀌면 다른 행동처럼 읽힌다.
- `nav` 우측 버튼도 같은 라벨이다. sticky `nav` 면 이게 네 번째 CTA 역할을 한다.
- 보조 CTA(데모 보기, 가격 보기)는 히어로에만 두고 시각 무게를 한 단계 낮춘다(outline 또는 text 버튼).

### 2.0.2 기능 섹션 고르기: grid · bento · alternating

| 조건 | 고를 섹션 | 이유 |
|---|---|---|
| 핵심 기능 2–3개, 각각 실제 화면이 있다 | `feature-alternating` | 기능 하나에 한 화면을 줘서 깊게 보여준다. 4개 넘으면 지루해진다 |
| 기능 4–7개, 중요도가 다르고 화면 조각이 있다 | `bento-grid` | 큰 타일 1–2개 + 작은 타일로 위계를 만든다. 타일마다 실제 화면이 있어야 산다 |
| 기능 4–6개, 비슷한 무게, 이미지가 없다 | `feature-grid` | 텍스트로 훑게 한다. 3열 아이콘 카드만 쓰지 말고 2열 텍스트 블록이나 표로도 쓴다 |
| 사용 사례(직군·상황)별로 화면이 다르다 | `tabs-showcase` | 탭 3–5개로 한 자리에서 전환한다 |
| 실제 순서가 있다(설치 → 연결 → 결과) | `how-it-works` | 순서일 때만 번호를 붙인다(LA-5) |

한 페이지에 기능 섹션은 두 종류까지 섞는다. 예: 핵심 2개는 `feature-alternating`, 나머지 6개는 `feature-grid` 로 압축.
같은 골격(제목 + 3열 카드)이 세 번 반복되면 LA-3 이다.

### 2.1 saas-product

1. `nav` — 로고, 링크 4–6개(제품·가격·고객 사례·문서), 우측 로그인 + 주 CTA. 링크가 7개를 넘으면 정리한다.
2. `hero-split` (실제 화면이 있으면) 또는 `hero-product` (화면이 크고 가로로 넓으면) 또는 `hero-type` (화면이 없으면).
   필요한 것: 한 문장 약속(H1), 대상과 결과를 담은 보조 문장 1–2줄, 주 CTA, 보조 CTA, CTA 아래 마찰 제거 한 줄("카드 등록 없이 14일").
3. `logo-cloud` 또는 `proof-strip` — 실제 고객사 로고 5–8개, 또는 출처가 있는 수치·평점 한 줄. 없으면 뺀다.
4. `feature-alternating` 2–3행 — 약속을 지키는 핵심 기능. 행마다 실제 화면 + 제목(결과 중심) + 설명 2–3줄.
5. `feature-grid` 또는 `bento-grid` — 나머지 기능을 압축. 연동·보안·권한 같은 "있어야 안심되는" 항목이 여기 온다.
6. `cta-band` (중간) — 작동 방식을 다 본 시점이 첫 결심 지점이다.
7. `testimonials` — 실명·직함·회사가 있는 후기 2–3개. 후기가 기능 하나를 구체적으로 말할수록 좋다.
8. `pricing` — 플랜 2–3개, 추천 플랜 하나 강조, 월/연 토글. 가격이 아직 없으면 뺀다.
9. `faq` — 5–8문항. 해지·환불·데이터·보안·결제 수단.
10. `cta-band` — 히어로와 같은 CTA.
11. `footer` — 링크 3–4열, 약관·개인정보처리방침, 유료 서비스면 사업자 정보.

### 2.2 app-download

1. `nav` — 로고와 "앱 받기" 버튼 하나면 충분하다. 링크를 늘리면 설치에서 시선이 샌다.
2. `hero-split` — 왼쪽 약속 + 스토어 버튼, 오른쪽 실제 앱 화면 1–2장(폰 프레임). 데스크톱은 QR 을 같이 둔다(5장).
3. `proof-strip` — 스토어 평점·리뷰 수·다운로드 수. 스토어에서 확인되는 값만 쓴다.
4. `feature-alternating` 3행 — 화면 하나에 기능 하나. 앱은 화면이 곧 기능이라 alternating 이 가장 잘 맞는다.
5. `testimonials` — 스토어 리뷰 인용(닉네임·날짜·별점). 출처가 스토어임을 밝힌다.
6. `faq` — 지원 OS 버전, 요금, 회원 탈퇴, 데이터.
7. `cta-band` — 스토어 버튼 반복.
8. `footer`

### 2.3 waitlist (사전 등록)

1. `nav` — 로고만. 출시 전이라 갈 곳이 없다.
2. `hero-centered` 또는 `hero-type` + 인라인 폼(이메일 또는 휴대폰 1필드 + 버튼). 폼이 히어로 안에 있어야 전환이 난다.
   필요한 것: 약속, 출시 예정 시기(정해졌다면), 등록 혜택(있다면).
3. `feature-grid` — 무엇이 달라지는지 3–4개. 화면이 없으니 텍스트 중심이다.
4. `how-it-works` — 등록 후 일어나는 일(등록 → 출시 알림 → 혜택 적용). 진짜 순서라 번호가 맞다.
5. `faq` — 언제 출시하나, 비용, 알림 수단, 등록 취소.
6. `cta-band` 또는 `form` 반복 — 히어로 폼과 같은 필드.
7. `footer` — 수집 주체와 개인정보처리방침 링크.

### 2.4 service-agency

1. `nav` — 서비스·사례·프로세스·문의.
2. `hero-type` — "누구의 무엇을 어떻게 해결한다" 한 문장. 에이전시는 제품 화면 대신 결과물이 증거라 큰 글자로 시작한다.
3. `logo-cloud` — 실제 고객사(공개 동의를 받은 곳만).
4. `content-list` — 대표 사례 3–6개: 썸네일 + 고객 + 한 줄 결과. 서비스 소개보다 먼저 둔다. 에이전시의 구매 결정은 "비슷한 일을 해 봤나"에서 나기 때문이다.
5. `feature-grid` — 서비스 항목(2열 텍스트 블록이 3열 아이콘 카드보다 낫다).
6. `how-it-works` — 실제 진행 단계(상담 → 제안 → 계약 → 진행 → 납품)와 기간.
7. `testimonials` — 고객 담당자 실명·직함.
8. `form` — 상담 신청: 이름, 연락처, 회사, 예산 범위(선택형), 일정, 내용. 6필드 이내.
9. `footer` — 사업자 정보.

### 2.5 event

1. `announcement-bar` — 마감일·잔여석처럼 실제 날짜가 있는 소식만. 없으면 뺀다.
2. `nav` — 프로그램·연사·장소·FAQ 앵커 + "신청하기".
3. `hero-media` 또는 `hero-type` — 행사명, 날짜·시간, 장소(온라인이면 플랫폼), 주 CTA. 이 셋이 첫 화면에 없으면 실패다.
4. `text-block` — 무엇을 왜 하는지 3–5줄.
5. `content-list` — 연사(사진·이름·소속·세션 제목), 그다음 시간표(시간 | 세션 | 연사 표).
6. `pricing` — 티켓 종류·가격·조기 할인 마감일.
7. `media-text` — 장소: 지도 이미지 + 주소·교통·주차.
8. `faq` — 환불, 녹화본 제공, 입장 방법.
9. `cta-band` → `footer` — 주최 정보.

### 2.6 creator (개인 브랜드)

1. `nav` — 이름 또는 로고, 글·강의·소개·구독.
2. `hero-split` — 본인 실사진 + 누구를 위해 무엇을 하는지 한 문장 + 주 CTA(구독 또는 강의 보기). 사진이 없으면 `hero-type`.
3. `proof-strip` — 구독자 수, 출간·강연 이력 등 확인 가능한 것만.
4. `content-list` — 대표 글·영상·강의 3–6개.
5. `newsletter` — 무엇을 얼마나 자주 보내는지 한 줄 + 이메일 1필드.
6. `testimonials` — 수강생·독자 후기(실명 또는 동의받은 닉네임).
7. `pricing` — 강의·컨설팅을 판매할 때만.
8. `faq` → `footer`

## 3. 첫 화면 계약 (Above the fold)

### 데스크톱 1440×900

브라우저 크롬을 빼면 실제 높이는 약 780–820px 이다. 이 안에 다음이 보여야 한다.

- `nav` 64–72px.
- H1 전체(2줄 이내 권장), 보조 문장, 주 CTA. CTA 버튼 하단이 y 640px 을 넘지 않게 둔다.
- 증거 하나: 제품 화면의 윗부분, 로고 띠, 평점 중 하나. 히어로 아래에 다음 섹션이 40–80px 걸쳐 보이면 스크롤할 내용이 있다는 신호가 된다.
- 히어로 높이를 `100vh` 로 꽉 채우지 않는다. 다음 섹션이 안 보이면 페이지가 거기서 끝난 것처럼 보인다.

### 모바일 390×844

주소창·하단 바를 빼면 실제 높이는 약 660–700px 이다.

- `nav` 56px: 로고 + 주 CTA(작게) + 메뉴 버튼. 주 CTA 를 메뉴 안에 숨기지 않는다.
- H1 은 28–34px 로 3줄 이내, 보조 문장 3줄 이내, 주 CTA 는 폭 100%·높이 48–52px.
- 첫 화면 안에 CTA 가 들어와야 한다. 제품 화면은 CTA 아래에서 시작해 잘려 보여도 된다(스크롤 유도).
- 히어로가 지나가면 하단 고정 CTA 바(56–64px + safe-area)를 띄울 수 있다. 히어로 CTA 가 보이는 동안은 숨긴다.

## 5. 한국 관례

- **카카오톡 공유 미리보기**: 국내 유입의 상당수가 카톡 링크 공유로 들어온다. `og:image` 는 1200×630 으로 만들고, 로고와
  핵심 문구는 가운데에 모은다. 미리보기 비율이 화면마다 달라 가장자리가 잘릴 수 있어서다. `og:title` 은 40자 안쪽,
  `og:description` 은 한 문장. 공유 직후 이 카드가 랜딩의 실질적인 첫 화면이 된다.
- **카카오톡 채널 상담 버튼**: 오른쪽 아래 플로팅 원형 버튼(52–56px, 화면 끝에서 16–24px)이 흔하다. 모바일에서 하단 고정
  CTA 바와 겹치지 않게 바 위로 올리고, 폼 입력 중에는 숨긴다. 채팅이 주 CTA 를 대신하지 않게 시각 무게를 한 단계 낮춘다.
- **사전 등록 폼**: 국내에서는 이메일보다 휴대폰 번호(문자·알림톡 발송)를 많이 받는다. `inputmode="tel"`, 입력하면서
  `010-0000-0000` 으로 하이픈을 자동으로 넣는다. 개인정보 수집·이용 동의(필수)와 마케팅 정보 수신 동의(선택)는 체크박스를
  따로 두고, 선택 동의는 기본값을 체크 해제로 둔다. 각 동의 옆에 "보기" 링크로 수집 항목·목적·보유 기간을 펼친다.
- **앱 다운로드**: 데스크톱 방문자는 그 자리에서 설치할 수 없으니 QR(120–160px)과 스토어 배지를 같이 보여준다. 모바일은
  OS 를 감지해 해당 스토어 버튼 하나를 크게, 다른 스토어는 텍스트 링크로 둔다. 문자로 설치 링크 받기 폼을 두기도 한다.
- **사업자 정보**: 유료 서비스나 전자상거래로 판매한다면 푸터에 사업자 정보(상호·대표자·사업자등록번호·통신판매업 신고번호·
  주소·연락처 등)를 표시한다. 정확한 항목은 법령과 결제·플랫폼 사업자 안내를 확인한다. 12–13px 회색 텍스트로 두되 대비
  4.5:1 은 지킨다.
- **가격 표기**: `19,000원`처럼 숫자 + '원', 천 단위 쉼표. 월 요금이면 "/월", 부가세 포함 여부를 가격 아래 한 줄로 적는다.
- **헤드라인 줄바꿈**: 한글 헤드라인은 `word-break: keep-all` 로 단어 중간에서 끊기지 않게 하고, 데스크톱에서 의미 단위로
  줄을 나누려면 `<br>` 대신 `text-wrap: balance` 나 폭 제한(max-width 14–18em)을 먼저 쓴다.
- **이벤트·프로모션**: 신청 기간, 당첨자 발표일, 경품 제공 방식, 개인정보 보유 기간을 FAQ 나 유의사항 블록에 텍스트로 둔다.

## 6. 구조 질문 하나

> **보여줄 수 있는 실제 제품 화면(스크린샷·영상)이 있나요?**

| 선택지 | 바뀌는 것 |
|---|---|
| 여러 장 있다 (3장 이상) | `hero-split` 또는 `hero-product`, 핵심 기능은 `feature-alternating` 이나 `bento-grid` 로 화면마다 한 칸씩 |
| 한두 장 있다 | 가장 좋은 한 장을 `hero-product` 에 쓰고, 기능은 텍스트 중심 `feature-grid`(2열 블록) + `how-it-works` |
| 아직 없다 | `hero-type`. 기능은 텍스트·표로, 작동 방식은 단계 다이어그램(HTML 로 그린 흐름)으로. `bento-grid`·`feature-alternating` 은 쓰지 않는다 |

코드에서 화면 이미지(`public/screenshots`, `og-image`, 앱 스토어 에셋)를 찾을 수 있으면 묻지 않고 "있음"으로 둔다.

## 8. 콘텐츠가 없을 때

없는 콘텐츠는 지어내지 않는다. 섹션을 빼거나, 자리에 `TODO(카피)`·`TODO(이미지)` 를 남기고 브리프의 콘텐츠 인벤토리에 적는다.

| 섹션 | 없는 것 | 처리 |
|---|---|---|
| `logo-cloud` | 공개 가능한 고객사 | 섹션 생략. 업종 일반명("스타트업 300곳") 같은 우회 문구도 쓰지 않는다 |
| `testimonials` | 실명 후기 | 생략. 베타 사용자 인용을 받을 계획이면 `TODO(카피)` 1개 자리만 |
| `stats`, `proof-strip` | 출처 있는 수치 | 생략. 수치 대신 구체적 사실(지원 형식, 연동 목록)을 `feature-grid` 에 |
| `hero-*` 의 화면 | 제품 스크린샷 | `hero-type` 으로 바꾼다. 실제 UI 컴포넌트 일부를 HTML 로 렌더해 보여주는 건 괜찮다(지어낸 수치는 넣지 않는다) |
| `feature-alternating`, `bento-grid` | 기능별 화면 | `feature-grid` 텍스트 블록 2열, 또는 기능 비교 표 |
| `pricing` | 확정 가격 | 섹션 생략, CTA 를 "출시 알림 받기"·"문의하기"로 |
| `faq` | 실제 질문 | 답을 아는 질문만 쓴다. 답이 정해지지 않은 항목(환불 규정 등)은 `TODO(카피)` 로 남긴다 |
| `how-it-works` | 확정된 절차 | 생략. 순서가 확실할 때만 쓴다 |
| `demo` | 영상 | 생략. 정지 화면 + 캡션 3개가 빈 플레이어보다 낫다 |
