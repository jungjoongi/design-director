# 콘텐츠·포트폴리오 페이지 패턴

블로그 목록·글 상세·포트폴리오 홈·케이스 스터디·문서(docs) 화면의 구조를 정할 때 읽는다. 섹션 이름은
`${CLAUDE_PLUGIN_ROOT}/references/sections.md` 의 id 만 쓴다.

이 유형에서는 콘텐츠가 곧 디자인이다. 글이면 읽기 편한 줄 길이와 행간이, 작업물이면 큰 썸네일과 실제 산출물이 화면의
대부분을 만든다. 장식(히어로 그라데이션, 기술 스택 진행 바, 등장 효과)을 더할수록 콘텐츠가 약해 보인다.

## 1. 하위 유형 (Subtypes)

| 하위 유형 | 목적 | 대표 예시 성격 | 기본 섹션 순서 요약 |
|---|---|---|---|
| `blog-index` | 읽을 글 고르기 | 개인·팀 기술 블로그, 뉴스레터 아카이브 | nav → 소개 한 줄 → content-list → pagination → newsletter → footer |
| `article` | 끝까지 읽게 하기 | 블로그 글, 회고, 튜토리얼 | article-header → article-body + toc → code-block → author-box → related-posts → newsletter |
| `portfolio-home` | 작업물로 실력 증명 | 디자이너·개발자 포트폴리오 | nav → hero-type → project-grid → text-block(소개) → cta-band(연락) → footer |
| `case-study` | 일하는 방식 증명 | 프로젝트 상세 | case-study-hero → 문제 → 과정(실제 산출물) → 해결 → 결과 → 배운 것 → prev-next |
| `docs` | 필요한 답을 빨리 찾기 | 제품·라이브러리 문서 | 상단바(검색) → docs-sidebar · 본문 · toc 3단 → prev-next |

백틱으로 쓴 하위 유형 이름(`blog-index` 등)은 페이지 분류명이다. 섹션 id 가 아니므로 브리프 섹션 표에는 쓰지 않는다.

## 2. 섹션 순서와 이유

### 2.1 blog-index

1. `nav` — 블로그 이름, 글·태그·소개·구독(RSS·뉴스레터). 링크 5개 이하.
2. 소개 한 줄 — `text-block` 1–2줄: 무엇에 대해 쓰는지. 큰 히어로를 두지 않는다. 블로그 첫 화면의 주인공은 최신 글이다.
3. `content-list` — 최신순. 항목: 날짜(`2026.10.14`) · 제목(18–20px, 굵게) · 요약 1–2줄 · 태그. 리스트 형태가 기본이다.
   모든 글에 실제 커버 이미지가 있을 때만 카드 그리드(2–3열)를 쓴다. 이미지가 없는 카드 그리드는 같은 상자의 반복(LA-1)이 된다.
4. 태그·시리즈 필터(`filter-bar` 변형) — 목록 위 가로 칩 또는 오른쪽 사이드. 글이 30개 이상일 때부터 의미가 있다.
5. `pagination` — 번호 또는 "이전 글 더보기". 연도별 묶음(2026 / 2025)도 아카이브 탐색에 좋다.
6. `newsletter` — 무엇을 얼마나 자주 보내는지 한 줄 + 이메일 1필드.
7. `footer` — RSS, 소셜 링크, 저작권.

### 2.2 article

1. `article-header` — 카테고리·시리즈 → 제목(데스크톱 32–40px, 모바일 24–28px) → 요약 1–2줄 → 글쓴이 · 발행일 · 수정일 ·
   읽는 시간. 날짜가 없으면 기술 글은 신뢰를 잃는다(언제 기준의 정보인지 모른다).
2. 커버 이미지(선택, `article-header` 변형) — 본문 폭 또는 그보다 조금 넓게. 높이는 첫 화면의 50% 이하로, 본문 첫 문단이 보이게.
3. `article-body` + `toc` — 본문은 한 줄 34–40em(한글 약 35–40자), 16–18px, 행간 1.7–1.8, `word-break: keep-all`.
   h2 · h3 에 앵커 링크. 목차는 데스크톱(1200px 이상)에서 오른쪽 sticky, 현재 읽는 절을 강조한다. 모바일은 본문 위에
   접힌 "목차" 한 줄.
4. `code-block` — 언어 라벨 + [복사] 버튼(오른쪽 위, 누르면 "복사됨" 1.5초), 가로 스크롤(줄바꿈하지 않는다), 13–14px 고정폭,
   파일 이름이 있으면 탭 형태로. 본문 폭보다 넓게 빼도 된다.
5. 공유(`article-body` 끝 한 줄) — 링크 복사 · 카카오톡 · X. 글 끝에 둔다(다 읽은 사람이 공유한다).
6. `author-box` — 사진(실사진 또는 생략) · 이름 · 한 줄 소개 · 링크 2–3개.
7. `related-posts` — 3개, 같은 시리즈·태그 우선. 시리즈 글이면 이전·다음 편을 먼저.
8. `newsletter` 또는 댓글 — 둘 중 하나를 주 행동으로.

왜 이 순서인가: 독자는 제목·날짜로 "읽을 가치가 있나"를 정하고(1), 본문을 읽고(3–4), 다 읽은 시점에만 저자와 다음 글에
관심을 갖는다(6–7). 저자 소개를 글 위에 크게 두면 읽기 전에 스크롤만 늘어난다.

### 2.3 portfolio-home

1. `nav` — 이름(로고 대신), 작업 · 소개 · 연락(이메일 링크). 이력서 PDF 링크.
2. `hero-type` — 한두 문장: 누구를 위해 어떤 일을 하는 사람인지("결제·정산 화면을 설계하는 프로덕트 디자이너. 복잡한 금융
   흐름을 단순한 단계로 바꾼다"). 높이는 첫 화면의 40–50% 이하로 두고 그 아래에 작업물이 보여야 한다.
3. `project-grid` — 대표 작업 4–6개, 2열 큰 썸네일(16:10 또는 4:3, 비율 통일). 항목: 썸네일 → 프로젝트 이름 → 한 줄 결과
   ("가입 단계 7→3단계") → 역할 · 연도. 썸네일은 실제 화면·산출물 크롭. 가짜 기기 목업 안에 지어낸 화면을 넣지 않는다.
4. `logo-cloud` (선택) — 함께 일한 회사. 공개해도 되는 곳만.
5. `text-block` 소개 — 5–8줄. 일하는 방식, 관심 분야, 경력 요약. 기술 스택은 진행 바가 아니라 목록이나 문장으로.
6. 연락(`cta-band` 변형: 메일 링크) — 이메일 주소를 텍스트로(복사 버튼). 폼보다 메일 링크가 채용 담당자에게 빠르다.
7. `footer` — 링크(GitHub · LinkedIn · 블로그), 저작권.

### 2.4 case-study

1. `case-study-hero` — 프로젝트 이름 → 한 줄 결과 → 메타 표(역할 · 기간 · 팀 구성 · 내가 맡은 범위 · 도구) → 대표 이미지.
   "내가 맡은 범위"가 핵심이다. 팀 프로젝트에서 무엇이 본인 몫인지 모르면 평가할 수 없다.
2. 문제 — `text-block`: 누가 어떤 상황에서 무엇을 못 했는지. 근거(인터뷰, 데이터, 문의 내용)를 한 줄씩.
3. 과정 — `media-text` 반복: 실제 산출물(스케치, 와이어프레임, 리서치 노트, 다이어그램, 이전 버전 화면) + 그때 내린 결정과 이유.
   버린 안을 보여주면 판단력이 보인다.
4. 해결 — `feature-alternating` 또는 `gallery`: 최종 화면을 기능·흐름 단위로.
5. 결과(`text-block`, 측정값이 있으면 `stats`) — 측정한 수치(출처·기간과 함께) 또는 정성적 결과(사용자 반응, 출시 여부). 측정하지 않았으면 그렇게 쓴다.
6. 배운 것(`text-block`) — 3–5줄. 다시 한다면 다르게 할 것.
7. `prev-next` 다음 프로젝트 — 큰 썸네일 링크 하나. 목록으로 돌아가지 않고 다음 작업으로 이어지게.

### 2.5 docs

1. `nav` 상단바 — 로고 · 버전 선택 · 검색(⌘K / Ctrl K, 넓게) · GitHub · 테마 전환. 높이 56–64px.
2. `docs-sidebar` — 왼쪽 240–280px, 섹션 트리(시작하기 → 가이드 → API 레퍼런스 순), 현재 문서 강조, 스크롤 독립.
3. 본문(`article-body`) — 폭 34–40em(본문 16–17px 이면 약 560–680px): 브레드크럼 → 제목 → 한 줄 설명 → 본문(`code-block`, 주의·팁 콜아웃, 표) → "이 페이지 수정" · 마지막 수정일.
4. `toc` — 오른쪽 200–240px, 현재 문서의 h2 · h3.
5. `prev-next` 이전 · 다음 문서 — 본문 끝 큰 링크 두 개.

3단(사이드바 · 본문 · 목차)은 1280px 이상에서만. 1024–1279px 은 목차를 본문 위로 접고, 1023px 이하는 사이드바도 드로어로 숨긴다.

## 3. 첫 화면 계약 (Above the fold)

### 데스크톱 1440×900

- `article`: 제목 · 요약 · 글쓴이 · 날짜 · 본문 첫 문단이 보인다. 오른쪽 `toc` 가 보인다. 커버 이미지가 첫 화면을 다 덮지 않는다.
- `blog-index`: 소개 한 줄 아래 최신 글 5–7개(리스트형)가 보인다.
- `portfolio-home`: 이름·하는 일 한두 문장 + 첫 줄 작업물 2개의 썸네일 윗부분이 보인다.
- `case-study`: 프로젝트 이름 · 한 줄 결과 · 메타 표(역할 · 기간 · 맡은 범위)가 보인다.
- `docs`: 사이드바 · 제목 · 설명 · 첫 절이 보이고 검색창이 상단바에 있다.

### 모바일 390×844

- `article`: 제목 24–28px 3줄 이내 + 메타 1줄 + 본문 시작. 본문 좌우 여백 20px, 글자 16–17px.
- `portfolio-home`: 소개 2–3줄 + 첫 썸네일이 걸쳐 보인다.
- `docs`: 상단바(메뉴 · 검색) + 제목 + 본문. 사이드바는 드로어, 목차는 본문 위 접힌 한 줄.

## 5. 한국 관례

- **한글 본문**: `word-break: keep-all`, 16–18px, 행간 1.7–1.8, 한 줄 35–40자. 한글은 라틴보다 글자 밀도가 높아 같은 폭에서
  더 빽빽해 보이므로 행간을 라틴 기준(1.5)보다 넉넉히 둔다. 한글 이탤릭은 쓰지 않는다(강조는 굵기로). 자세한 값은
  `${CLAUDE_PLUGIN_ROOT}/references/korean-typography.md` 를 따른다.
- **날짜**: `2026.10.14` 형식. 기술 글은 발행일과 수정일을 둘 다 보여준다.
- **공유**: 링크 복사와 카카오톡 공유가 기본이다. 카톡 미리보기용 `og:image`(1200×630, 제목을 가운데 안전 영역에)를 글마다 만든다.
- **시리즈**: 국내 블로그 플랫폼(브런치·velog 등)에 익숙한 독자는 시리즈 묶음과 "이전 편 · 다음 편"을 기대한다. 시리즈 글이면
  `article-header` 위에 시리즈 이름과 편수를 단다.
- **포트폴리오**: 국내 채용에서는 PDF 포트폴리오·이력서를 같이 요구하는 경우가 많아 `nav` 에 이력서(PDF) 링크를 둔다. 연락처는
  이메일 텍스트로. 회사 작업물은 공개 범위를 확인하고, 공개할 수 없는 화면은 흐림 처리 + "보안상 일부 가림" 표시.
- **댓글**: 개발 블로그는 GitHub 기반 댓글(giscus 등)을 쓰는 경우가 많다. 댓글이 없으면 글 끝에 이메일·소셜 링크로 대신한다.

## 6. 구조 질문 하나

> **글이 주인공인가요, 작업물이 주인공인가요?**

| 선택지 | 바뀌는 것 |
|---|---|
| 글이 주인공 (블로그) | 첫 화면은 `content-list`(리스트형, 날짜 · 제목 · 요약). 상세는 `article-body` 34–40em + `toc` + `code-block`. 이미지는 보조 |
| 작업물이 주인공 (포트폴리오) | 첫 화면은 `hero-type` 한두 문장 + `project-grid` 2열 큰 썸네일. 상세는 `case-study-hero` → 과정 → 결과. 글은 있으면 `content-list` 로 아래에 |
| 둘 다 | 홈은 작업물 4개 + 최근 글 3개(리스트). 내비에서 "작업"과 "글"을 나란히. 무게는 둘 중 하나에 더 준다 |

라우트에 `/docs` 나 MDX 문서 트리가 있으면 이 질문 대신 `docs` 로 추론한다. `/posts/[slug]` 만 있으면 글, `/work`·`/projects` 가
있으면 작업물을 추론 기본값으로 둔다.

## 7. 흔한 실수

| 실수 | 증상 | 패턴 | 처방 |
|---|---|---|---|
| 자기소개 히어로 | "안녕하세요, 열정적인 개발자 ○○입니다" + 손 흔드는 이모지 | CP-4, IC-1 | 무엇을 누구를 위해 하는지 한두 문장. 증거는 바로 아래 작업물로 |
| 기술 스택 진행 바 | React 90%, Figma 85% | — | 측정할 수 없는 숫자다. 목록이나 "어디에 썼는지" 문장으로 |
| 너무 긴 줄 | 본문이 1200px 폭을 꽉 채운다 | — | 34–40em(한글 35–40자) |
| 회색 위 회색 본문 | 옅은 회색 배경에 연회색 본문, 대비 4.5:1 미달 | CO-7 | 본문은 대비 7:1 근처, 보조 텍스트만 회색 |
| 날짜 없는 글 | 언제 쓴 글인지 모른다 | — | 발행일 · 수정일을 `article-header` 에 |
| 커버 없는 카드 그리드 | 이미지 없는 글 카드 9개가 같은 상자로 반복 | LA-1, LA-3 | 리스트형 `content-list` |
| 지어낸 목업 | 가짜 앱 화면을 기기 프레임에 넣은 썸네일 | CP-5 | 실제 화면·산출물 크롭. 없으면 타이포 썸네일(8장) |
| 갤러리뿐인 케이스 스터디 | 최종 화면 10장, 설명 없음 | — | 문제 → 과정 → 결과 순서와 맡은 범위 |
| 문단마다 등장 효과 | 스크롤할 때마다 글이 떠오른다 | MO-1 | 읽는 화면에는 등장 효과를 쓰지 않는다 |
| 모바일 목차가 본문을 가림 | 떠 있는 목차 버튼·패널이 글을 덮는다 | — | 본문 위 접힌 한 줄 |

## 8. 콘텐츠가 없을 때

| 섹션 | 없는 것 | 처리 |
|---|---|---|
| `content-list` 썸네일 | 글마다 커버 이미지 | 리스트형으로. 자동 생성 그라데이션 썸네일을 넣지 않는다 |
| `project-grid` 썸네일 | 작업물 이미지 | 타이포 썸네일(프로젝트 이름 + 한 줄 결과를 큰 글자로, 단색 배경). 지어낸 화면 금지 |
| `media-text`(case-study 의 과정) | 산출물(스케치·리서치) | 결정과 이유를 글로 쓰고 산출물 자리는 생략. 사진이 없다고 스톡 이미지를 쓰지 않는다 |
| 결과 수치 | 측정값 | "측정하지 않음"이라 쓰고 정성 결과(출시, 사용자 반응)를 적는다. 수치를 지어내지 않는다 |
| `author-box` 사진 | 사진 | 이름 + 한 줄 소개만. 기본 아바타 일러스트를 넣지 않는다 |
| `related-posts` | 관련 글 3개 | 글이 적으면 섹션 생략하고 "전체 글 보기" 링크 |
| `newsletter` | 실제 발송 계획 | 생략. 계획이 있으면 주기를 정한 뒤 `TODO(카피)` |
| `logo-cloud` | 공개 가능한 고객사 | 생략 |
| 소개 `text-block` | 소개 글 | `TODO(카피)` 한 자리. 형용사 나열("열정적인, 꼼꼼한")로 채우지 않는다 |
